description: Run every gate the project has and fix what fails
---

Run `bun run check`. For each failure, fix the cause rather than loosening the rule, then run it again until it passes. If you changed a feature or a core module (`src/features/<name>/` or `src/features/core/<name>/`), make sure its `TIMELINE.md` has a new Decisions or History line. Never loosen the core rule to make a check pass: a core module holds components only, or services and helpers only; a module with both, or with a page, moves out of core.

Lint refuses every comment in a file unless the file opens with `// software-factory-lint allow comments` (rule `no-comment`), and refuses commented-out code, TODO markers and a comment repeated in two places even then. It cannot tell whether an allowed comment is needed. Before you add that line to a file, or a comment to a file that has it, hold the comment to this test: without it, would the next person or agent likely change this code into a bug that no test catches, or miss a rule they need when they extend it? Code that looks wrong, unused or easy to simplify but is deliberate passes (a disabled option that another layer covers, an import kept at the top for speed, an export a platform finds by name). So does a known limit, written as `shortcut: <limit>, <when to fix>`. Everything else goes somewhere better: a fact into a name, a behaviour into a test and its title, a design choice into the feature's `TIMELINE.md`. Most changes should add no comments, and a comment that fails the test is deleted, not allowed.
